# ESP32-S3 智能冰箱贴架构与工作流设计

## 1. 文档目标

本文档用于固定“冰箱小精灵”首版 Demo 的工程架构、AI 接入方式、设备工作流、公共数据接口和测试验收标准。当前阶段以 ESP32-S3 设备直连 OpenAI-compatible API 为正式 AI 路线。

项目按 `ESP32-S3-DevKitC-1 N8R8` 设计，即 8 MB Flash + 8 MB PSRAM。当前工程中的 `sdkconfig` 仍需继续按 N8R8 实板约束收敛，后续固件实现时必须使用 8 MB Flash、启用 PSRAM、`ota_0` 大主固件、`ota_1` 小型本地 recovery 和 LittleFS 数据分区。

首版 Demo 的目标是打通以下闭环：

- ESP32-S3 主控显示、触摸、OV3660 拍照、传感融合、库存摘要、提醒、MQTT、OTA 与诊断。
- `TS040HDS02CP-B1620A` 720 x 720 QSPI/SPI 屏幕与 FT6336U 触摸。
- 光照、IMU、24GHz/25GHz 人体存在毫米波雷达、麦克风、蜂鸣器等本地交互外设。
- 主控直连 OV3660 摄像头，完成拍照、JPEG/帧缓冲管理，并把文本/结构化上下文和后续图片数据通过 HTTPS 直接提交给 OpenAI-compatible API。
- 设备端直连真实 AI API 完成食材识别、语义解析、菜谱生成和购物清单，保留本地 Mock 兜底。
- 小程序或移动端完成配网绑定、库存确认、位置管理和隐私设置。

## 2. 总体架构

系统采用“ESP32-S3 单主控端侧节点 + 设备直连 AI API + 本地/Web 管理”的分层架构。

```text
用户
  |
  | 触摸 / 语音 / 靠近 / 开门 / 拍照
  v
ESP32-S3 主控
  - LVGL UI
  - FT6336U 触摸
  - OV3660 摄像头采集
  - 光照 / IMU / 毫米波雷达融合
  - 本地库存摘要与提醒队列
  - Capture Job 与上传状态
  - HTTPS AI API / OTA
  |
  | HTTPS /chat/completions 等 OpenAI-compatible API
  v
OpenAI-compatible API 服务
  - 文本对话
  - 结构化任务输出
  - 后续多模态图片识别
  |
  | 结构化 JSON 结果
  v
屏幕 / Web 运维面板 / 后续移动端
  - 配网与 AI API 配置
  - 识别结果确认
  - 存储位置选择
  - 菜谱 / 购物清单 / 设置
```

设计原则：

- 端侧负责确定性：开门判断、离线库存摘要、临期提醒、基础 UI、定时器和异常提示都必须本地可用。
- AI 直连负责智能性：图片识别、复杂语义解析、菜谱推荐和购物清单由设备通过 HTTPS 直接调用 OpenAI-compatible API。
- 主控直接采集图片：OV3660 直连 ESP32-S3，主控负责拍照、帧缓冲/JPEG 管理、请求封装和结果解析。
- 首版不使用 TF/SD 卡：主控不长期保存图片原图，只保存任务状态、错误码、必要元数据和最终库存结果。
- 所有业务变更事件化：库存新增、修改、消耗、删除、位置移动都使用事件和版本号同步。
- AI 结果不直接入库：必须经过规则校验和用户确认，低置信度结果进入待确认流程。
- API Key 安全边界：首版 Demo 允许用户通过 Web 面板写入设备 NVS；串口响应和日志不得回显明文。该方案适合竞赛和原型验证，公开部署前应评估 NVS 加密或 Key 轮换。

## 3. 硬件拓扑

### 3.1 ESP32-S3 主控

主控使用 `ESP32-S3-DevKitC-1 N8R8`，职责如下：

- 初始化屏幕、触摸、OV3660 摄像头、传感器、音频、蜂鸣器和网络。
- 运行 LVGL 页面和本地状态机。
- 保存本地结构化缓存：库存摘要、提醒队列、位置模板、断网待补传事件、拍照任务状态。
- 通过 HTTPS 直连 AI API；如后续需要 MQTT/远程同步，只作为独立运维扩展，不参与 AI 主链路。
- 执行 OTA、日志上报和健康监控。

### 3.2 屏幕与触摸

屏幕依据 `doc/屏幕技术文档Specification_TS040HDS02CP-B1620A_V1.2(1).pdf` 设计：

| 参数 | 取值 |
| --- | --- |
| 型号 | TS040HDS02CP-B1620A |
| 尺寸 | 4.0 inch |
| 分辨率 | 720 x 720 |
| 显示驱动 | TR230S |
| 显示接口 | QSPI / SPI |
| 触摸驱动 | FT6336U |
| 触摸接口 | I2C |
| 逻辑输入电平 | 3.3 V |
| 屏幕供电 | VCC 5 V，典型电流约 186 mA |
| 背光 | 模组已集成背光驱动，典型 40 mA |
| 最大时钟 | SPI 4-wire / QSPI 4SDA 均为 100 MHz |

首版固件实现约束：

- 首选 QSPI 4SDA 模式；SPI 4-wire 仅作为调试保底。
- LVGL 使用局部刷新与 20 到 40 行双缓冲，不使用全帧频繁刷新。
- 背光使用 PWM 调光，夜间和无人状态降低亮度。
- 触摸 FT6336U 挂在 I2C 总线，触摸中断接 GPIO。
- `WAIT#` 用于判断 TR230S 是否允许发送命令，调试阶段建议接入。

### 3.3 摄像头

摄像头使用 `OV3660` 模组，直接接入 ESP32-S3 主控：

- 主控通过 camera 驱动完成初始化、曝光/白平衡预热、帧采集和 JPEG/帧缓冲管理。
- 拍照任务由主控状态机触发，后续图片识别优先由主控把图片或压缩后的图像数据直接提交给 OpenAI-compatible 多模态 API。
- 首版不接 TF/SD 卡，不保存长期图片原图；上传失败时只保留任务状态、错误码、时间戳和用户可读提示。
- 摄像头引脚必须结合实物模组、屏幕 QSPI、I2S 麦克风、I2C 总线和启动绑带脚复核后再固定。
- 开发阶段从低分辨率、低帧率和较低 XCLK 起步，确认 PSRAM、水位、Wi-Fi 和 UI 刷新稳定后再提高质量。

### 3.4 传感和交互外设

| 外设 | 推荐方案 | 职责 | 注意事项 |
| --- | --- | --- | --- |
| 光照 | BH1750 或光敏电阻模块 | 辅助判断开门光照突变 | I2C/ADC 电平必须为 3.3 V |
| IMU | MPU6050 或 ICM-42688 | 检测门体姿态变化和震动 | 需固定在门体随动位置 |
| 人体存在 | HLK-LD2410C/LD2410B 或同类 24GHz/25GHz 模块 | 靠近唤醒、有人保持、夜间无人判断 | 优先 UART 配置距离/灵敏度，GPIO 只作为快速有人/无人输入 |
| 麦克风 | INMP441 或 ICS-43434 | 命令词或语音输入 | I2S 引脚需避开摄像头和屏幕总线 |
| 蜂鸣器/小喇叭 | 有源蜂鸣器或小喇叭 | 定时器和提醒音 | GPIO 不得直接承担超额电流 |

人体存在毫米波雷达说明：

- 同类 24GHz/25GHz 人体存在模块可检测运动、微动和静止人体，适合冰箱前停留时保持亮屏。
- 模块正面不要被金属遮挡，外壳窗口优先使用塑料材料。
- 厨房内风扇、窗帘、宠物、门体震动和金属反射可能造成误触发，需要通过距离门限和保持时间抑制。
- 雷达只提供“有人/靠近”上下文，不单独作为开门判断依据。

### 3.5 建议引脚策略

| 功能 | GPIO | 说明 |
| --- | --- | --- |
| LCD_CS | GPIO10 | 屏幕片选，低有效 |
| LCD_SCLK | GPIO12 | SPI/QSPI 时钟 |
| LCD_D0 | GPIO11 | SPI MOSI / QSPI DATA0 |
| LCD_D1 | GPIO13 | SPI MISO / QSPI DATA1 |
| LCD_D2 | GPIO14 | QSPI DATA2 |
| LCD_D3 | GPIO9 | QSPI DATA3 |
| LCD_RST | GPIO7 | 屏幕复位，低有效 |
| LCD_WAIT | GPIO6 | TR230S WAIT#，建议接入 |
| TOUCH_INT | GPIO15 | FT6336U 触摸中断 |
| TOUCH_RST | 不接 | N8R8 安全排线中 GPIO16 让给 OV3660 D7 |
| I2C_SDA | GPIO4 | 触摸、IMU、OV3660 SCCB 共用 |
| I2C_SCL | GPIO5 | I2C 时钟 |
| RADAR_RX | GPIO21 | 雷达 TX -> ESP32 RX |
| RADAR_TX | GPIO20 | ESP32 TX -> 雷达 RX |
| RADAR_OT2 | 不接 | GPIO19 让给 OV3660 PCLK |
| CAMERA_D0-D7 | GPIO17/18/8/3/46/48/45/16 | OV3660 8-bit DVP 数据 |
| CAMERA_SYNC | GPIO2/38/19/47 | VSYNC/HREF/PCLK/XCLK，禁用 GPIO35/36/37 |
| MIC_BCLK / SPK_BCLK | GPIO40 | I2S 共用 BCLK |
| MIC_WS / SPK_LRC | GPIO41 | I2S 共用 WS |
| MIC_DIN | GPIO42 | INMP441 数据输入 |
| SPK_DIN | GPIO39 | MAX98357A 数据输出 |
| UART0 | GPIO43/44 | 下载与调试 |

当前 N8R8 安全排线禁止外接 GPIO35、GPIO36、GPIO37，并且不再使用 GPIO0。GPIO3、GPIO45、GPIO46、GPIO48 仍用于 OV3660，属于高风险脚，实物上电前需要断电复核并建议串联小电阻。

## 4. ESP32-S3 固件架构

固件采用组件化分层。后续实现时建议把 `main/main.c` 收缩为启动编排入口，把业务放入独立组件。

| 组件 | 职责 |
| --- | --- |
| `bsp` | 板级 GPIO、I2C、SPI/QSPI、I2S、LEDC、摄像头时钟、按键、电源与公共硬件初始化 |
| `display` | TR230S 屏幕驱动、QSPI/SPI 面板 IO、背光、显示刷新 |
| `touch` | FT6336U 初始化、触摸坐标读取、触摸事件上报 |
| `camera` | OV3660 初始化、帧缓冲/JPEG 管理、拍照任务、上传状态与错误码 |
| `ui` | LVGL 页面、主题、页面路由、弹窗、动画、二维码与状态卡片 |
| `sensors` | BH1750/光敏、IMU、人体存在毫米波雷达采样、滤波、校准和事件输出 |
| `state_machine` | 靠近、开门、关门、夜间、离线、拍照、提醒等情境状态 |
| `storage` | NVS、LittleFS、库存快照、位置模板、提醒队列、断网事件队列、拍照任务元数据 |
| `network` | Wi-Fi、SNTP、HTTP 客户端、TLS 证书、重连策略 |
| `mqtt_protocol` | 可选远程同步扩展：MQTT 连接、主题订阅、消息编码/解码、QoS、幂等处理 |
| `audio` | I2S 麦克风、命令词、录音片段、蜂鸣器提醒 |
| `ota` | 版本检查、下载、校验、回滚、升级状态上报 |
| `diagnostics` | heap/PSRAM 水位、任务看门狗、错误码、日志、coredump 上报 |

### 4.1 FreeRTOS 任务

| 任务 | 优先级 | 触发方式 | 主要职责 |
| --- | --- | --- | --- |
| `gui_task` | 高 | LVGL tick / UI 队列 | 刷新页面、动画、触摸事件处理 |
| `sensor_task` | 中高 | 20 到 50 Hz | 读取传感器、滤波、生成传感事件 |
| `camera_task` | 中 | 拍照命令 / AI 队列 | OV3660 预热、采集、JPEG/帧缓冲管理、上传任务状态 |
| `state_task` | 高 | 事件驱动 | 门状态和情境状态机、生成 UI/提醒事件 |
| `net_task` | 中 | Wi-Fi/HTTPS 事件 | 联网、重连、时间同步、AI API 请求前置检查 |
| `storage_task` | 中低 | 存储队列 | 快照写入、pending 队列、日志滚动、拍照元数据写入 |
| `audio_task` | 中高 | I2S DMA | 命令词、录音、提醒音 |
| `ai_task` | 中 | AI 任务队列 | 组装上下文、直连 OpenAI-compatible API、解析 JSON、进入确认流程 |
| `ota_task` | 低 | 夜间/手动 | OTA 检查、下载、重启 |
| `watchdog_task` | 中 | 5 s 周期 | heap、PSRAM、任务心跳和异常上报 |

任务之间通过 FreeRTOS Queue、EventGroup 和轻量消息结构通信。UI 不直接读写网络、摄像头和存储，必须通过事件队列解耦。

### 4.2 本地状态机

```text
BOOT
  -> PROVISIONING
  -> IDLE

IDLE
  -> APPROACH       毫米波雷达检测到人体存在或距离进入阈值
  -> NIGHT_IDLE     夜间且雷达长时间无人
  -> OFFLINE        网络异常

APPROACH
  -> DOOR_OPEN      光照突变 + IMU 姿态变化
  -> IDLE           超时无人操作或雷达无人保持

DOOR_OPEN
  -> DOOR_CLOSED    姿态恢复 / 光照下降
  -> CAPTURE        用户拍照 / 语音拍照 / 小程序命令

CAPTURE
  -> AI_PENDING     OV3660 拍照成功，AI API 请求已创建
  -> ERROR          摄像头初始化、采集、PSRAM 或上传失败

AI_PENDING
  -> CONFIRMING     AI 候选项返回
  -> OFFLINE        网络中断，任务进入 pending 状态

CONFIRMING
  -> INVENTORY_SYNC 用户确认入库

INVENTORY_SYNC
  -> IDLE           同步成功或本地缓存完成
```

开门判断初值：

- `light_delta`: 1 s 内 lux 增量大于 80，或相对增幅大于 60%。
- `angle_delta`: 2 s 内绕门轴姿态变化大于 15 到 30 度。
- `vibration_peak`: 加速度模长短时峰值大于 0.15 g。
- `presence_hold`: 毫米波雷达检测到人体存在后保持 10 到 20 s，仅作为靠近和上下文增强。
- `presence_distance`: 首版建议只响应冰箱前 0.2 到 1.5 m 的人体存在，具体阈值按安装位置调参。
- `debounce`: 状态切换最小间隔 800 ms。

## 5. AI 直连架构

首版正式 AI 链路采用设备直连 OpenAI-compatible API：

```text
storage 本地结构化数据
  -> ai_context 生成任务上下文
  -> ai_client 组装 HTTPS 请求
  -> OpenAI-compatible /chat/completions 或后续多模态接口
  -> 设备解析结构化 JSON
  -> 用户确认
  -> 本地库存事件/快照更新
```

AI 系统的详细任务类型、上下文注入、记忆边界、USB/Web 调试命令见 `doc/AI系统设计架构.md`。当前固件 `ai_client` 不再只是连通性探针，而是首版设备直连 AI API 的正式入口；`ai_context` 负责把库存、提醒、偏好、记忆摘要和任务规则整理成最小上下文。

| 模块 | 职责 | 说明 |
| --- | --- | --- |
| `ai_client` | 保存 API Base URL、模型、API Key，执行 HTTPS 请求 | API Key 保存在 NVS，响应和日志不回显明文 |
| `ai_context` | 生成任务上下文、输出约束和 Mock 结果 | 后续真实调用前先用它统一 prompt 和 schema |
| `storage` | 提供库存、提醒、偏好、记忆摘要和离线队列 | 当前为种子 JSON + NVS，后续替换为 LittleFS |
| `usb_protocol` | 暴露 Web 调试命令 | 支持配置、聊天测试、上下文预览和项目 AI 任务 |
| 可选远程服务 | 远程同步、OTA、日志分析、备份 | 不参与 AI 调用链路 |

### 5.1 设备直连 AI API

首版至少提供：

- `chat_assist`: 厨房助手问答。
- `recognize_ingredients`: 食材识别候选，后续接入摄像头图片或多模态输入。
- `inventory_parse`: 用户表达转库存变更建议。
- `recipe_generate`: 根据库存和偏好生成菜谱。
- `shopping_list_generate`: 根据库存缺口生成购物清单。
- `reminder_explain`: 解释临期提醒。
- `voice_intent_parse`: 语音文本意图解析。

实现要求：

- API Base URL、模型名、系统提示词和 API Key 由 Web 面板配置。
- 请求必须走 HTTPS，并依赖 SNTP 校时和系统证书包。
- 所有 AI 输出必须先做结构化解析和业务规则检查，再进入用户确认流程。
- API Key 只允许保存在 NVS，不得出现在串口响应、日志、进度文档或 Git 仓库中。
- Mock 结果必须保留，用于无网络、额度异常或比赛现场兜底。

## 6. 公共接口

### 6.1 可选 MQTT 主题

MQTT 不参与首版 AI 链路，只作为后续远程同步和运维扩展保留。

| 方向 | Topic | Payload 摘要 | QoS |
| --- | --- | --- | --- |
| 设备上报 | `fridge/{home_id}/{device_id}/state` | 在线状态、RSSI、页面、版本、heap/psram | 1 |
| 传感事件 | `fridge/{home_id}/{device_id}/sensor` | door_state、lux、angle、presence、distance、timestamp | 1 |
| 库存变更 | `fridge/{home_id}/{device_id}/inventory/event` | add/update/delete/consume/move 事件 | 1 |
| 远程命令 | `fridge/{home_id}/{device_id}/cmd` | capture、show_card、start_timer、ota_check | 1 |
| 拍照任务 | `fridge/{home_id}/{device_id}/capture/status` | request_id、image_id、status、error_code、uploaded | 1 |
| 远程 AI 摘要 | `fridge/{home_id}/{device_id}/ai/result` | 可选同步 AI 结果摘要，不作为主返回路径 | 1 |
| 错误日志 | `fridge/{home_id}/{device_id}/error` | error_code、stack、free_heap、context | 0/1 |

所有消息必须包含：

- `schema_version`
- `event_id` 或 `request_id`
- `device_id`
- `timestamp`
- `payload`

### 6.2 HTTPS 接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `{api_base_url}/chat/completions` | POST | 设备直连 OpenAI-compatible 文本/结构化任务 |
| 后续多模态接口 | POST | 设备直连图片识别或视觉问答，按所选服务商兼容格式实现 |
| `/api/v1/ota/check` | POST | 可选远程 OTA 查询 |
| `/api/v1/ota/report` | POST | 可选远程 OTA 状态上报 |

## 8. 核心工作流

### 8.1 启动流程

1. 初始化日志、heap/PSRAM 检查、任务看门狗。
2. 初始化 NVS、LittleFS、设备配置、库存快照和提醒队列。
3. 初始化 BSP、屏幕、背光、触摸、传感器、毫米波雷达、麦克风和蜂鸣器。
4. 初始化 OV3660 摄像头，执行低分辨率探测和 PSRAM 水位检查。
5. 启动 LVGL，显示启动页和硬件自检状态。
6. 初始化 Wi-Fi，成功后 SNTP 校时。
7. 加载 AI API 配置；若已保存 Base URL、模型和 Key，则进入可测试状态。
8. 加载库存摘要和 UI 页面，进入 `IDLE`。

### 8.2 配网与绑定

1. 主控进入配网模式，Web 运维面板通过 USB/Web Serial 连接设备。
2. Web 面板发送 SSID 和密码，主控连接 2.4GHz Wi-Fi。
3. Wi-Fi 成功后执行 SNTP 校时，确保 HTTPS 证书校验可用。
4. Web 面板写入 OpenAI-compatible API Base URL、模型、系统提示词和 API Key。
5. 主控执行 `test_ai_chat` 或项目 AI 任务，确认设备直连 API 可用。

### 8.3 开门提醒

1. `sensor_task` 采集光照、IMU 和毫米波雷达存在/距离事件。
2. `state_task` 根据光照突变、姿态变化和震动峰值判断 `DOOR_OPEN`，毫米波雷达只作为靠近和有人上下文。
3. 主控立即读取本地 `reminder_queue.json` 和 `inventory_snapshot.json`。
4. UI 展示临期 Top 3、剩余天数、存储位置标签和推荐菜入口。
5. 开门事件写入本地事件/日志；后续如启用远程同步，再通过 MQTT 或 HTTPS 补传。

### 8.4 拍照入库

1. 用户在屏幕、小程序或语音中触发拍照。
2. 主控创建本地 `capture_job`，携带 `request_id`、`mode`、`created_at`。
3. `camera_task` 预热 1 到 2 帧，采集 OV3660 图像并生成 JPEG/上传缓冲。
4. 主控把图片或后续压缩后的图像输入与结构化上下文一起提交给 OpenAI-compatible API。
5. 设备解析 AI 返回的候选食材、数量估计、置信度和疑点。
6. 设备本地做 JSON 格式、置信度和业务规则校验。
7. 屏幕或 Web 面板展示确认页，用户确认名称、数量、到期日和存储位置。
8. 确认后生成本地库存事件。
9. 主控更新本地库存快照和提醒队列；后续如启用远程同步，再异步上传事件。

### 8.5 离线容错

主控离线时：

- 保留当前库存快照和提醒队列。
- 开门提醒继续走本地快路径。
- 新增、消耗、删除、位置移动事件写入 `pending_queue.jsonl`。
- 拍照任务只保留任务状态、错误码、时间戳和用户提示，不承诺保存图片原图。
- 网络恢复后按时间顺序补传业务事件；需要图片识别时提示用户重新拍照或重试仍在内存生命周期内的上传任务。

### 8.6 OTA 运维

1. 可选远程服务或本地运维工具发布新版本信息。
2. 主控在夜间或用户手动触发时调用 OTA 检查接口。
3. 正常情况下主固件运行在 `ota_0`；升级前云端保存可回退版本和哈希，但云端备份不能作为唯一兜底。
4. 本地 recovery 固件常驻 `ota_1`，只保留 NVS、Wi-Fi、串口 JSON Lines、诊断和后续下载/写入主固件能力，不链接 LVGL、摄像头、AI、语音等大模块。
5. 主固件健康检查失败、用户串口命令或后续启动失败计数触发时，切换到 `ota_1` recovery。
6. recovery 从云端或串口侧取得新主固件，校验签名和哈希后覆盖 `ota_0`，成功后切回 `ota_0` 启动。
7. 如果联网、TLS 或 OTA 逻辑在主固件中损坏，仍可依赖本地 recovery 进行恢复；如果 recovery 自身损坏，则需要重新串口烧录。

## 9. 分区建议

按 8 MB Flash 设计：

| 分区 | 类型 | 建议大小 | 用途 |
| --- | --- | --- | --- |
| `nvs` | data/nvs | 64 KB | Wi-Fi、设备凭证、用户偏好 |
| `otadata` | data/ota | 8 KB | OTA 启动选择 |
| `phy_init` | data/phy | 4 KB | 射频校准 |
| `ota_0` | app/ota_0 | 3584 KB | 主固件大分区 |
| `ota_1` | app/ota_1 | 1024 KB | 本地 recovery 小分区 |
| `assets` | data/littlefs | 1536 KB | 字体、图标、颜文字、音效 |
| `cache` | data/littlefs | 704 KB | 库存、提醒、位置、断网队列、日志、拍照任务元数据 |
| `coredump` | data/coredump | 64 KB | 异常转储 |

当前 `sdkconfig.defaults` 指向 `partitions_recovery.csv`，其中 `ota_0` 为 3584 KB 主固件分区，`ota_1` 为 1024 KB 本地 recovery 分区。后续实现时需要在 `sdkconfig` 中启用自定义分区表、8 MB Flash、PSRAM、LittleFS 和 recovery OTA 启动状态。首版不为图片原图预留本地长期存储空间。

生成 recovery 镜像时使用独立 profile：`idf.py -B build_recovery -DFRIDGE_RECOVERY_BUILD=ON -DSDKCONFIG="sdkconfig.recovery" -DSDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.recovery.defaults" reconfigure build`。该镜像应写入 `ota_1` 偏移，不能直接对 recovery build 目录执行默认 `idf.py flash`，否则 ESP-IDF 会按普通 app 流程把镜像写到 `ota_0`。

## 12. 关键假设与风险

### 12.1 假设

- 实际开发板为 ESP32-S3 N8R8。
- 屏幕为 TS040HDS02CP-B1620A，TR230S 初始化资料可以从供应商或手册补齐。
- 摄像头使用 OV3660 直连主控，不额外引入独立拍照子设备。
- 首版不新增 TF/SD 卡，不承诺离线保存图片原图。
- 人体存在模块以 HLK-LD2410C/LD2410B 或同类 24GHz/25GHz UART/GPIO 模块为基准。
- AI API 服务商暂不绑定，首版通过 OpenAI-compatible API Base URL 和模型名在设备端配置。
- 真实 AI 优先，但必须保留本地 Mock 结果作为比赛现场兜底。

### 12.2 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 当前 sdkconfig 仍需收敛 | 无法稳定支持 OTA、本地资源缓存和 PSRAM 摄像头缓冲 | 后续实现第一步核对 8 MB、PSRAM 和分区表 |
| TR230S 初始化资料不完整 | 屏幕无法点亮或刷新异常 | 向商家索取初始化代码，SPI 模式作为保底 |
| 720 x 720 刷新压力大 | UI 卡顿、Wi-Fi 抖动、内存不足 | 局部刷新、20 到 40 行双缓冲、减少动画 |
| OV3660 占用 GPIO 和 PSRAM | 与屏幕、I2S、I2C 冲突或拍照时内存不足 | 引脚实物复核；低分辨率起步；拍照期间监控 heap/PSRAM |
| 摄像头弱光识别差 | AI 识别准确率低 | 补光、固定拍摄距离、低置信度确认 |
| 毫米波雷达误触发 | 路过或反射导致频繁唤醒 | 设置距离门限、保持时间和夜间策略；雷达不参与单独开门判定 |
| 直连 AI API 延迟、额度不足或 Key 失效 | 现场 Demo 失败 | 限制 max_tokens、保留 Mock 结果、在 Web 面板显示明确错误 |
| API Key 保存在设备 NVS | 开发板丢失或固件被读出时可能泄露 | 串口/日志不回显明文；公开部署前评估 NVS 加密和 Key 轮换 |
| 冰箱金属影响 Wi-Fi 和雷达 | 掉线、雷达盲区或反射 | 天线离金属面 5 到 8 mm，雷达前方使用塑料窗口并避开金属遮挡 |
| 无 TF/SD 卡图片缓存 | 离线时不能长期保存图片原图 | 文档和 UI 明确提示；离线只保留任务状态，恢复后重新拍照 |

## 13. 后续代码落地顺序

后续开始实现代码时，建议严格按以下顺序推进：

1. 新增自定义分区表，修正 `sdkconfig` 为 8 MB Flash、PSRAM、大主固件 + 小 recovery、LittleFS。
2. 重构 ESP32-S3 主控为组件化目录，保留 `main.c` 作为启动编排。
3. 先点亮屏幕和触摸，再接入 LVGL 页面。
4. 接入光照、IMU 和毫米波雷达，完成靠近/开门状态机。
5. 接入 Wi-Fi、HTTPS AI API 和本地缓存。
6. 接入 OV3660 摄像头，完成拍照、帧缓冲/JPEG 管理和 HTTPS 上传。
7. 完成设备直连 AI API 的上下文注入、结构化解析和用户确认流程。
8. 完成拍照识别入库、开门提醒、菜谱推荐和 OTA；远程同步作为后续扩展。
